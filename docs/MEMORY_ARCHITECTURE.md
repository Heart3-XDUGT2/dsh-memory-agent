> 起因：2026-09-25 讨论中他问「记忆架构到底怎么运行，那个记忆图和具体的记忆内容
> 为什么完全对不上」。本文用**活库实测数字**回答，不引任何设计理想。
> 取数：`~/.dsh/echo/echo.db` 只读（2026-09-25）。

## 一、两个方向、五张表（一句话版）

```
① 写入方向（每轮 turn/end 之后，一次 LLM 调用产三样东西）
   QQ/私聊消息 ──▶ 她的回复
        │  lib/index.js 轮次捕获（走 session/event 的追加流）
        ▼
   反思 EXTRACT / Judge         ← 一次 LLM 调用
        ├── candidates     ──▶ episodic_memory   句子：发生了什么事
        ├── triples        ──▶ graph_nodes/graph_edges   三元组：谁—关系—谁
        └── pendingThreads ──▶ 悬置话题（她惦记着、还没结掉的事）
        └── 顺带            ──▶ user_profile（画像/称呼）、agent_state（情绪）

② 读取方向（每轮 pre-step，lib/engine.js:86-129 组装成「一封信」）
        ┌──────────────────────────────────────────────┐
        │ ①【关联知识路径】  ← graph_query（种子→BFS→路径文本）│ ← 图谱唯一的用途
        │ ②【情景记忆】      ← retrieve（DMAE 排序 + L0 强制占位）│
        │ ③ 悬置话题 / 想念行 / 议程 / 时间锚 / 纪律尾          │
        └──────────────────────────────────────────────┘
```

**一句话**：**记忆是「发生了什么」的句子，图谱是「谁和谁什么关系」的三元组**，
它们是**同一次反思的两种产物**，落在两张表里，**彼此不引用**。
图谱不是记忆的可视化，记忆也不是图谱的展开。

## 三、「对不上」的五个真实原因

### 1. 形状不同（最根本，不是 bug）
`judge.py:441` 给 LLM 的三元组 schema 就是「主语(短名词) / 关系(2~6 字) / 宾语(短名词)」。
所以**只有能被压缩成短名词关系的记忆才会进图谱**；情绪、细节、对话语气、
「她说明不抢月饼的真正原因是需要排队」这种句子，在图上根本没有位置。
反过来，图谱里也**没有正文**——`用户 -参加-> 校园跑` 这条边不告诉你哪天跑的、跑得多累。

### 2. 增长速率差两个数量级
记忆几乎每轮都长（183 条），图谱只在抽得出三元组时才长（28 节点 / 33 边）。
实测图谱确实还活着：最新的两个节点 `她`、`浪费时间` 与最新一条记忆
（#183「不抢月饼是因为要排队、不喜欢浪费时间」）**同一时刻**（`1790310798`）写入，
最新边 #33 `不喜欢` 的激活度 99.5 —— 但它长得**慢且稀**。

### 3. 两边都在重复，措辞还漂移
图谱里同一件事被写成多个节点/多条边：

```
西安电子科技大学 / 西电 / 西安电子科技大学计算机专业 / 新工科大学 / 新工科
大学生 / 大一学生 / 大一新生
Echo记忆架构 / AI记忆架构 / 记忆架构 / Echo后端架构 / 后端架构 / agent后端架构 / 网站后端架构
用户 -希望打造-> Echo / 用户 -期望打造-> Echo / 用户 -想打造-> Echo
用户 -就读于-> 新工科大学 / 用户 -读于-> 新工科大学
```

记忆侧同样：#42/#45/#65/#87/#88/#90/#93 七条 L0 都在说「西电/新工科/大一」。
「同键同文才算想起」只在**完全同文**时命中，换个说法就各长一坨。

> **⚠️ 追记（2026-09-25，写完本文后跑 `scripts/memory-doctor.mjs` 实测）**：
> 上文「L0 现在有 7 条说同一件事 / L0 是每轮强制注入」**说重了**。实测 17 条
> L0 里 **16 条早已 `is_active=0`**（旧版本换代留下的），现役 L0 只剩 1 条 —— 
> 所以「L0 重复每轮白烧注意力」这条**不成立**。真正在重复的是两个非 L0 层：
> 空层（60 条现役）与 `reflection`（65 条现役）；体检实测重复组 18 组、
> 可让位 25 行，全在这两层。去重的收益因此不是「省 token」，而是
> **同一件事别在她心里存两份互相打脸的版本**（检索时两版都可能被捞出来）。

### 4. 两表之间**没有任何回指**（结构性原因）
`graph_nodes` 与 `graph_edges` 的列里有 `properties`、`evidence` 吗？——**没有**
（实测列名：节点 = node_id/name/node_type/is_protected/properties/last_accessed/
activation/…/temporal_status/owner_key；边 = edge_id/source_id/target_id/relation/
weight/…/slot/is_active/superseded_by/layer）。
所以**从图上一个点点不回它来自哪条记忆**；反过来只有 reflection 行有
`evidence='依据:记忆129'` 这种单向线索。**两边一根线都没连**——这才是他
「完全对不上」的直接观感来源。

### 5. 面板上的数字与库里的列不是一回事
节点 `activation` 在 DSH **从不被写**（实测全 0），图谱页的活跃度是
**前端现算**的（`lib/store.js:647` 注释明说；`lib/engine.js:503` 同）。
边有真 activation（`graph_reinforce` → `apply_ltp` 会写）。
⇒ 同一个「图谱页」，节点圆的大小/颜色来自现算、边的粗细来自库列，
观感上就更难和记忆对上。

## 五、要不要动架构？

**不动。** 这套「一次反思 → 句子 + 三元组 + 悬置话题」的双形状设计是 A 的原创，
也是本项目的答辩卖点（关系网 × 情景记忆双通道）。上面四件都是**接线与数据卫生**，
不是重构。参考材料里那些分层记忆/DMAE 变体/向量检索**一律不引入**（见
`docs/RELAY_PLAN.md` D10「不做」清单）。
