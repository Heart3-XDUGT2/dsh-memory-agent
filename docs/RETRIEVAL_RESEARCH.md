# 检索升级:开源与学术侧的现成解法(取证 + 方案)

> 2026-09-27。**本文件不改任何代码**,只做取证与选型。
> 起因:他问「检索记忆是不是有点简陋了」,我实测发现 **13/21 轮她只拿到 1 条记忆** ——
> 这直接造成「她没什么可说的」,和「冷」是同一件事的两面(见另一次取证)。

## 一、问题重述(带实测数字)

`python/engine/retrieve.py` 现状:纯字面包含五档 + `总分 = hits×2 + R×2 + 情感×0.1`。

活库实测(`audit_logs.injected_memories`,100 行样本):

| 指标 | 实测 |
|---|---|
| 含【情景记忆】的注入 | 21 条 |
| **其中只注入 1 条的** | **13 条** |
| 逐字完全相同的正文 | 21 条里 11 条(都是同一条「设计灵感来自风又音理」) |
| 注入条数分布 | `{1:13, 5:1, 2:5, 3:1, 6:1}` |

他随口一句(「在吗」「你在干嘛呢」「这是谁」)在这套匹配下几乎零命中 → 非 L0 全被丢
(`retrieve.py:147`) → 只剩 L0 强制占位。

**两个结构性缺陷:**

1. **只匹配 `keywords` 字段**。keywords 是上一轮抽取器 LLM 写的手气;它没写进「面试」,
   那条记忆就**永远检索不到**,内容里明明有也不行。这是"关键词彩票"。
2. **R 与命中平分秋色**。`hits×2 + R×2`:R 满值 2.0 = 一次满命中 2.0。一条不相关但
   新鲜的记忆能和切题的老记忆打平。

## 二、三份可以直接抄的现成实现

### ① `dsh-auto-memory` —— 完整 BM25 + CJK 2-gram + QueryPlan(本地资料)

`$env:USERPROFILE\Desktop\参考资料\dsh-auto-memory-main\lib\shadow-retrieval.js`

* `normalizeText()`(`:171`):NFKC + locale 无关小写。
* `tokenize()`(`:186`):**CJK 连续段切 2-gram**(每段上限 64)+ 保留 2~16 字完整词串 +
  Latin/数字/标识符走 `[A-Za-z0-9._\-/+]+`。
* `isStopWord()`(`:214`):哈工大停用词表 507 词。
* `buildQueryPlan()`(`:221`):按来源加权(trigger 1.0 / 最近用户 0.8 / 工具结果 0.6 /
  推理 0.5 / assistant 0.2)+ 预算截断 + `queryDigest`(可复现)。
* **打分(`:481-549`,最值得抄的一段)**:

  ```js
  idf = log(1 + (N - df + 0.5) / (df + 0.5))
  sat = (tf*(k1+1)) / (tf + k1*(1 - b + b*dl/avgdl)) / (k1+1)   // k1=1.2 b=0.75
  hitBm25 += idf * sat * term.weight
  termCoverage = clamp01(hitBm25 / totalIdf)                     // [0,1] 归一
  total = 0.72*termCoverage + 0.15*headingCoverage + 0.08*phraseMatch + 0.05*recency
  ```

  **对照我们的 `hits×2 + R×2`**:他把 recency 压到 **5%**,我们给到 **40%**;
  他按 idf 让稀有词权重大(「西电」比「喜欢」值钱),我们每个关键词一律 1.0 分;
  他做了归一化,分数可比可阈值;我们的分数量纲随查询长度漂。

### ② `dsh-company-kb` —— FTS5 + 中文二字组合 + trigram + RRF(**同为 DSH 插件**)

<https://github.com/wu81313-lab/dsh-company-kb>(MIT,纯离线,零外部服务)

它 README 的「为什么这样检索」表逐条都是实测结论,我把关键五行抄进下面的选型:

| 它的技术选择 | 它给的实测理由 |
|---|---|
| 预分词后写入 FTS | SQLite `unicode61` 不切中文:**原文直索 `MATCH '追溯'` 命中 0 条**,分词后可命中并 BM25 排序 |
| 加中文**二字组合** | `Intl.Segmenter` 把「袋线瓶线」切成 袋\|线\|瓶\|线,单字被丢弃后检索失败;补二字组合后 2 字查询才正常 |
| trigram 子串路 | 覆盖分词切不准的场合;2 字查询 trigram MATCH 无效 ⇒ 1 字查询退化为 LIKE |
| **RRF 融合** | **BM25 是负分、子串路是名次,量纲不同不能直接相加;RRF 只看名次** |
| 每文件最多 3 块 | 避免一份文件刷满结果,保证结果覆盖多个来源 |

模块划分也值得照:`lib/segment.js`(分词/查询构造/转义)、`lib/bigram.js`(相邻二字)、
`lib/store.js`(双 FTS5 索引 + RRF)、`lib/selftest.mjs`(**15 条金标查询**做验收)。

### ③ `NousResearch/hermes-agent` —— `cjk_unicode61` 二字索引 DDL

<https://github.com/NousResearch/hermes-agent/blob/245e4800/hermes_state_fts.py>
同一条路的另一个独立实现(session DB 的 FTS5 CJK bigram 索引),可作交叉印证。

## 三、我自己在本机验的事实(不照抄二手结论)

`python/sqlite3`(SQLite **3.50.4**),FTS5 可用:

| 查询 | ① 原样 `unicode61` | ② 预切二字组合(全部 gram AND) |
|---|---|---|
| 「西安电子科技大学」 | **0** | **1** |
| 「章鱼小丸子」 | **0** | **1** |
| 「就读」 | **0** | **1** |
| 「校园跑」 | **0** | **1** |
| 「大一」 | **0** | **2** |
| 「追溯」(语料里确实没有这个词) | 0 | 0 ✅ 该 0 就 0 |

* **中文在 `unicode61` 下全 0 命中** —— 与 dsh-company-kb 的实测一致。
* 预切二字后**全部恢复**;`AND` 精确、`OR` 召回更宽(「西安电子科技大学」OR 给 2 条)。
* **BM25 排序可用**:`ORDER BY bm25(b)` 返回负分(越负越好)⇒ 这也印证了 RRF 的必要性。
* **性能不是问题**:1000 条 × 200 字,**建索引 5 ms,单次查询 0.01 ms**(我们全库才 ~500 条)。

> 这条最要紧:**我们现在这套是纯 Python 内存里逐个 `in` 判断**,而 FTS5 是零依赖、
> 宿主自己就在用(`dsh-session-query-sqlite` 里 `CREATE VIRTUAL TABLE ... fts5(..., tokenize='unicode61')`)。

## 五、落地方案(分批,先零依赖)

### P0 —— 三步,零新依赖,当天可验

1. **索引正文,不只索引 keywords**。给 `episodic_memory` 建 **FTS5 外部内容表**,
   正文 = `summary` + `keywords`,**按 ②的做法预切二字组合**。
   > 这一步直接消灭"关键词彩票":抽取器没写「面试」也能搜到。
2. **配重换成 idf 加权覆盖率**(抄 ①的 0.72/0.15/0.08/0.05 骨架),
   `recency` 从 40% 压到 5% 量级;L0 强制占位(F5)与豁免语义**保持不变**。
3. **近重复抑制**:同一事实的换说法只留一条(照 ②的"每文件最多 3 块"思路,
   按 (layer, 归一化正文相似度) 去重),把 top_k 还给**不同**的记忆。

**验收口径**:重跑同一批 21 个真实查询样本,「只注入 1 条」的比例从 **13/21** 降下来;
自建 **15 条金标查询**(照 ②的 selftest),「零命中」全部有据可查。

### P1 —— RRF 多路融合(仍零依赖)

`BM25 路` + `图谱路(F6/F10/F11 的种子与 BFS)` + `强制 L0 路` 三路各自排名,
**RRF 只看名次**(①的负分 + 名次不可加,已被我实测印证)。
顺带把「查询扩展」做进来:查词命中图节点 ⇒ 该节点的边邻居与别名进扩展词 ——
这是最便宜的"语义"提升,手边的图终于用上。

### P2 —— 真语义(需他点头,成本最大)

embedding 列 + 余弦。参考 `dsh-auto-memory` 的做法:e5-small ONNX、
**池化/精度契约冻结自 R@5 0.925 基线**、模型文件 sha256 校验、离线优先。
代价:**venv ~400MB**(或 Node 侧 onnxruntime),与我们目前"零依赖"取向冲突。

**不建议照搬**:HippoRAG 的全量 OpenIE 建图(贵)、Zep 的四时间戳(已有)、
Mem0 的整合理念(已有更严格留空档语义)。

## 七、实测:六路对照(真实语料,`scripts/retrieval-bench.py`)

> ⚠️ **本节数字已知有偏(2026-09-27 补记)—— 请连着读,别单独引用。**
>
> 金标是我**照答案出的题**:24 条正例查询的题面词元里,**平均 69.8% 直接来自答案记忆**
> (13 条"字面类"查询全部 100%)。这是**方向性偏差,专门偏向词面方法** ——
> R0 与 R1 的分数**都被抬高**。
>
> 对照:他**真实说过的话**在语料里平均只有 **30.7% 的词面钩子,一半是 0%**
> (「在吗」「你在干嘛呢」「怎么就发一个字」)。即**真实问法里"没有主题"的轮次占一半,
> 而我的评测集里这类只占 22%**。
> (⚠️ 2026-09-27 复测:30.7% **无法精确复现** —— `conversation_log` 只留最近
> 100 轮,快照已变。同一把尺子实测为 **40.2%**(语料 = 摘要+关键词)/ **24.3%**
> (只摘要)。没有编数,两个口径都打在测台输出里。)
>
> **因此下面两条结论作废/撤回:**
> * 「R1 88.9%」→ 只能说"在**有偏样本**上是 88.9%",绝对值不可信;
>   方向(R1 优于 R0)仍可信 —— 因为**索引正文严格比只索引 keywords 信息更多**,这是逻辑性质,不是测量。
> * 「纯词面方法的天花板是 11.1%,所以向量只值 11.1%、不值 400MB」
>   → **撤回**。11.1% 是在我自己出的题上算的;按真实问法分布,语义缺口**远不止**。
>
> ✅ **已重建、三个漏洞已修**:测台按 query-first 重建(48 条 / 六档 / 负控 19;
> 逐字档的查询文本运行时从 `conversation_log` 逐字取出,**结构上不可能"改题凑命中"**),
> 检索的三个结构性漏洞也已修完 —— 新数字与前后对照见
> `docs/RETRIEVAL_PLAN.md` 的「八、实测数字」。**新金标下 R0 86.2% 反超
> R1 BM25 的 82.8%**:老分数(70.4% vs 88.9%)确实是词面白捡的。


跑法:`python scripts/retrieval-bench.py`(把活库拷一份出来,原库全程只读)。
语料:**179 条现役记忆**。金标:**27 条查询**(13 字面 + 3 冗余暴露 + 6 语义 +
2 图谱 + 3 负控)。`recall@5` 口径:top5 里出现任一可接受答案即算命中。

| 路 | 命中率 | 零命中率 | 冗余率(top5 内近重复) | 单次耗时 |
|---|---|---|---|---|
| **R0 现状**(生产代码) | 70.4% | 29.6% | 4.7% | 0.78 ms |
| **R1 BM25 正文** | **88.9%** | **11.1%** | 5.4% | **0.10 ms** |
| **R2 FTS5** | **88.9%** | **11.1%** | 5.4% | **0.09 ms** |
| R3 RRF 同族(R0+R1) | 77.8% | 22.2% | 4.7% | 0.01 ms |
| R4 RRF 异族(R1+图谱) | 88.9% | 11.1% | 5.3% | 1.65 ms |
| **R5 R1 去冗余** | **88.9%** | **11.1%** | **0.0%** | 0.08 ms |

(R1/R2 加停用词前是 85.2% / 14.8% / 7.1% —— 见下面"发现二"。)

### 发现一:现状答不上来时**不返回空,而是硬塞那条 L0 记忆**

三条负控(库里确实没有的东西)—— R0 全部返回 `[125]`:

| 查询 | R0 现状 | R1 BM25 |
|---|---|---|
| 量子纠缠 | **`[125]`** ✗ | `[]` ✓ |
| 明天股价 | **`[125]`** ✗ | `[]` ✓ |
| 他养的那只猫 | **`[125]`** ✗ | `[]` ✓ |

`#125` 就是那条 L0 强制占位记忆(「Echo 的设计灵感来自风又音理」)。
**零命中 ≠ 返回空,而是"她以为她有"** —— 这既是答非所问的机制,也是幻觉的来源。
R1 在三条负控上**全部正确返回空**。

### 发现二:二字组合必须配停用词,否则疑问词会污染整条查询

未加停用词时「他上的什么学校」全军覆没(R1 返回
`[256,224,209,221,166]` —— 全是"为什么不主动关怀我/QQ昵称/迎新晚会")。
原因:二字组合把 `什么/为什/么学` 这类**疑问词**也当成了检索词 ——
`#256「为什么你不主动关怀我」`靠 `什么` 命中。加了停用词表 + 丢弃单字后:

```
R1:  85.2% → 88.9%     零命中 14.8% → 11.1%     冗余 7.1% → 5.4%
```

**所以"抄 BM25"必须连停用词一起抄**(参考实现用哈工大 507 词表)。

### 发现三:同族 RRF 是**负增益**(-11.1pt),因为被坏排序器带偏

R3 把 R0 和 R1 融合,结果**比 R1 单独用还差**。逐条看得很清楚 ——
R3 几乎每条都把 `#125` 拖进 top5:

```
章鱼小丸子   R1  [169, 142, 143, 99, 3]      ← 干净
            R3  [169, 99, 142, 3, 125]      ← #125 挤进来
技术力      R1  [170, 174, 132, 134]
            R3  [132, 170, 174, 134, 125]   ← 同上
```

R0 的排序被「L0 强制占位 + R(新鲜度)占 40%」主导,`#125` 在它那里几乎总排第一。
**RRF 忠实传播了这个偏置。** 结论:R0 与 R1 都是字面匹配,信号高度相关;
**RRF 的用途是融合"不同的检索来源",不是把同一来源算两遍。**

### 发现四:图谱查询扩展在当前图结构下**零增益**、16 倍耗时

27 条里只有 6 条触发了扩展,而且扩出来的邻居词是:

```
章鱼小丸子他会做吗 → ['用户', '<称呼>']        ← 每条记忆都提到,无区分度
校园跑             → ['用户', '3km速度限制']
3km               → ['用户', '校园跑']
软件工程/一千美元   → ['用户']
```

R4 与 R1 的命中率**完全相同**(88.9%),耗时 1.65 ms vs 0.10 ms。
原因很实在:图里的节点名大多是**查询里已经出现**的词,而真正的邻居
(「学校」→「西安电子科技大学」)字面上接不上。

> **这不是说图没用**,而是说:**靠字面匹配做入口的扩展,救不了字面匹配的盲区。**
> 它要发挥,得先有语义入口(或谓词级扩展)—— 与"发现五"是同一个结论。

### 发现五:剩下的 11.1% 是**纯词面方法的天花板**

R1 失败的恰好是三条最"人话"的查询,且原因都是**答案记忆里根本没有那个词**:

| 查询 | R1 返回 | 为什么 |
|---|---|---|
| 他上的什么学校 | `[224,209,221,166,196]` ✗ | 答案记忆(#107/#111/#121)写的是「**新工科大学**」「**西电**」,没有「学校」二字 |
| 他把钱花哪了 | `[114,242]` ✗ | 答案写的是「**150 美元**」「**预算**」「**5 刀**」,没有「钱」 |
| 他昨天几点睡的 | `[]` ✗ | 需要时间推理,词面完全无交集 |

**这三条只有语义(embedding)或同义词表能救。** 它们占 3/27 = 11.1%。

### 发现六:去冗余是**免费赢**

R5 = R1 之后做近重复抑制:命中率**不变**(88.9%),冗余率 **5.4% → 0.0%**,
耗时几乎不变(0.09 ms)。代价是某些查询返回条数变少(如「数据结构」只返回 1 条)
—— 阈值(0.55)可调,但"宁可给一条真事实,不给五条同义"这个方向是对的。

### 算力:他的直觉是对的

```
27 条查询 × 6 路 = 162 次完整检索,合计 72.9 ms
→ 单次全路检索 ≈ 0.45 ms(语料 179 条,全部机械脚本,零大模型调用)
```

横向还有个意外:**R1/R2 比现状快约 8 倍**(0.10 ms vs 0.78 ms)——

### 这套实测自己的边界(老实说)
