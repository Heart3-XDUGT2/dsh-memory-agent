# 仓库纪律(reason 与留痕)

> 由来(2026-09-28):这天连着栽了两次**同一类**病 —— 一个机制**明明没跑或没通过**,
> 而人从外面看不出来。① 关心链断了 45 小时,`shouldCare` 明明是 true,面板上却什么都看不出
> (`careCount` 停在两天前);② 入站被主包 403 拒了每一条,理由只在宿主 stdout 里。
> 两次都不是"算法错",是**失败不可见**。
> 对照物:Cortico 把"否定与缺失"当成一等公民(`core/markers.ts` 全套记号、
> minecraft `stepLog{step,what,outcome,why,line}`、`precheck.ts:4` 的"全通过才静默")。
> 本仓从此照这条口径走。**两个仓(`dsh-echo` / `dsh-echo-qq`)都适用。**

## 五条硬规矩

### 1. `reason` 只许**枚举**,不许自由发挥

- 所有"为什么没做/为什么拒绝"的字段(`reason` / `skip` / `code`)取值必须是**固定集合里的一个**
  (`'not-master'` `'group-refused'` `'scope-off'` `'agent-busy'` `'too-long'` `'no-channel'` …)。
- 理由要能**直接 GROUP BY**:"最近 24 小时她没开口的原因分布"必须是一条 SQL 就能答的问题。
- 新的理由值 = 改代码 + 加枚举;不许临时拼一句人话(`'他刚才在忙所以算了'`)塞进去。
  - 人话留给**文案层**(面板/日志渲染时再翻译),不许进字段。
- **反例**(本仓真发生过):`care_silent` 只写不读、`follow_up_after=0` 被当成"永不主动提"
  而没有任何地方报出"这条账是哑的"。

### 2. **全通过才静默,任一否定必留痕**

- 一个链条(入站九步、关心链、出站 lease→发→ack)如果**每一步都通过**,可以**什么都不写**(静默)。
- 只要有**任何一步否定**(拒收 / 跳过 / 超时 / 降级 / 兜底),必须**留一行可查的痕**:
  数据库行、审计行、或 `incidents/` 里的一条。**只打日志不算** —— 宿主 stdout 我看不见。
- 判定"通过了没有"的口径要**显式**:`ok === true` 才算过,`undefined` / 缺字段一律**当成没通过**。

### 3. 豁免必须**带理由**,并且**自带自测**

- 任何"这里破例允许 X"的清单(打包门卫的允许清单、`pin-allow` 行、跳过检查的开关),
  必须写明**为什么**,而且**必须有一条测试证明这个豁免的边界**
  (例:`test/nohardcode.test.mjs` ⑦ —— 空理由不算豁免)。
- **豁免的粒度要尽可能小**:
  - ✗ 文件级(`name !== 'lib/onebot.js'` ⇒ 这个文件以后随便写)= **留了一个会长大的洞**;
  - ✓ 行级 + 理由必填(`// pin-allow: NapCat 握手鉴权 …`)。
  - 2026-09-28 已按这条把上面那个文件级豁免收窄成行级。

### 4. 枚举加了,**文案表必须同轮跟上**(2026-09-28 P2 加的一条)

- 规矩 1 说"人话留给文案层" ⇒ 那就必然存在**两张表要同步**:写入侧的枚举
  (`lib/heartbeat.js` 里 `logBeat(...)` 的调用点)与读侧的文案
  (`lib/care-report.js` 的 `REASON_TEXT`)。
- 同步不许靠自觉:`tests/care-report.test.js` 有一条**从源码里抠 reason 的测试**
  —— 把 `logBeat('care','xxx',…)` 里的枚举抠出来,逐个要求文案表认识它。
  新加一枚枚举却忘了文案 ⇒ 报告上会印「未知理由(新加的?要更新这张表)」,那条测试当场红。
- 推论(更一般):**凡"枚举 → 人话/样式/图标"的映射,都要有一条从源码抠枚举的测试**,
  否则两张表一定会慢慢长歪。

### 5. **载荷里新增的键,必须在 schema 里同时声明**(同轮)

- 宿主的工具输出校验是 `additionalProperties: false` 的**逐键**判定:
  payload 里多一个没声明的键 ⇒ **整条回执被拒**,而模型会把"回执被拒"读成"事情没做成"。
- 2026-09-28 P2 的实例:`echo_status` 的 `care` 从 v0.30.2 起就在 payload 里而 schema 没声明
  ⇒ 那个工具**每次调用都被拒**,连面板都拿不到状态。**不是本轮引入的**,是本轮才被抓住的。
- 所以:`npm run check:tools`(真实返回值 × 声明过的 schema,**每条出口都撞一遍**)
  **必须待在常跑的门里** —— 已并入 `npm run check`。只跑 `check` 不跑 `check:tools`
  等于这批事故一个都拦不住。

## 落地检查表(改完自己过一遍)

1. 这次改动里,有没有"某个分支悄悄不做"的地方?它的 `reason` 是枚举值吗?
2. 失败路径**在哪个持久面**能看见?(数据库行 / 审计行 / 状态接口字段 —— 三选一,不能是"日志")
3. 有没有新增豁免?理由写在哪一行?哪条测试钉住了它的边界?
4. 新增的字段是**只追加**吗?(老消费端 / 老验收脚本读的键一个不动 —— 跨仓独立发布,
   不许靠"两边一起升级"来收口;版本只做文案、能力名才做判定。)
5. 这条纪律本身有没有变成一纸空文?(有没有**测试**在钉它,而不是只有注释在说它?)
6. 新加的枚举,文案表跟上了吗?(规矩 4)新加的载荷键,schema 声明了吗?(规矩 5)
