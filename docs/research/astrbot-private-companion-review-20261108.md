# astrbot_plugin_private_companion 研究与 Echo 借鉴方案

日期：2026-11-08
研究对象：[menglimi/astrbot_plugin_private_companion](https://github.com/menglimi/astrbot_plugin_private_companion)，README 当前标注为 7.1.5 / `private_companion.v2`。

## 结论先行

这个项目在“产品化陪伴系统”与“后台生活引擎”方面，比 Echo 的公开说明完整得多；它最值得参考的是职责分层、主动行为候选生命周期、发送前复核/outbox、按角色与窗口的可见性、设置向导、外部记忆 Provider 契约，以及把运行诊断直接做成产品界面。

它没有直接证明在 Echo 的核心记忆召回、情绪建模或多人群聊理解上更强。README展示的是完整的能力范围和运行契约，不能替代同条件源码评测或真实用户对照。Echo不应照搬它的七项拓展能力，也不应把“有生活模拟”当成“记忆检索更好”。

## 一、它的整体架构值得借鉴什么

### 1. 宿主对话管线与陪伴后台分开

README明确把普通对话交给 AstrBot 核心管线，把插件职责限定为角色档案、生活与日程、长期记忆、当轮连续性、发送前表达编排、主动联系和扩展能力。

Echo目前也有类似分层，但公开文档没有把边界讲得这么清楚。可以在 Echo README增加一张“宿主/插件/QQ桥/模型”的职责图：

- DSH：会话、模型路由、原生循环和基础消息发送；
- Echo memory agent：人格、记忆、图谱、情绪、反思、主动行为、审计；
- QQ bridge：OneBot/官方接口、群聊补档、文件和回执；
- 模型服务：只负责生成，不拥有Echo数据库真相。

这能让使用者知道为什么要同时安装两个仓库，也能避免把桥接错误误认为记忆系统错误。

### 2. 角色全局默认 + 窗口级覆盖

它将角色作为全局默认，再允许私聊用户和群聊窗口独立覆盖。Echo目前有会话范围、陪伴开关和群聊开关，但公开README没有用一个清晰概念解释“角色默认—窗口覆盖—权限边界”的关系。

Echo可以加入：

- 全局角色默认；
- 私聊窗口覆盖；
- 群聊窗口覆盖；
- 覆盖优先级和回退规则；
- 哪些数据能跨窗口，哪些只能留在原窗口。

这比继续增加零散配置项更有价值。

### 3. 以“陪伴小屋”作为统一操作面

对方把配置、感知、理解、决策、行动、产出、表达、自我和治理放进一个统一入口，并支持首次使用引导、性能模式和局部启停。

Echo已经有新版设置、记忆、情绪、审计和维护页面，但仍偏“多个工具页”。可以借鉴它的导航层次，把Echo面板明确成：

- 自我：人格、称呼、角色档案；
- 记忆：情景记忆、核心记忆、图谱、反思；
- 情绪：整体状态、主人关系、衰减与历史；
- 现场：当前会话、群聊上下文、主动候选；
- 治理：审计、权限、回执、失败与降级；
- 维护：备份、迁移、恢复和数据边界。

## 二、记忆架构对比

### 对方项目公开描述的记忆能力

README把记忆写成一个角色生活系统的一部分，包括：

- 来源记忆、用户画像、共同经历；
- 语义向量与关键词混合召回；
- 增量召回；
- 每日记忆反思；
- 自动提取互动纪念日；
- 启动恢复与后台修复队列；
- 外部记忆 Provider 接口；
- 私聊和群聊可见性边界；
- 归档、撤回和权限不符记录不重新召回。

### Echo已有的强项

Echo的实现更明确地区分了：

- 情景记忆与核心身份事实；
- 时间状态：发生时间、得知时间、过去、计划、未知；
- 相关性检索与常在场记忆；
- 图谱关联查询和路径证据；
- recall_count、half_life、last_recalled、superseded_by等治理字段；
- Python完整检索与JS降级路径；
- 注入前的旧称呼改写；
- 反思提取与审计关联。

这些是Echo的核心竞争力，不能被对方的功能数量掩盖。

### 最值得借鉴的新增方向

1. **记忆来源和可见性页面化**：每条记忆显示来源、所属角色、可见范围、当前状态、是否被替代、最近召回时间。
2. **恢复队列**：把“启动后待修复”“检索失败待重试”“迁移后待确认”从日志变成可观察队列。
3. **互动纪念日作为记忆派生物**：只有原话明确支持、日期可追溯、去重成功时才创建；它应是派生视图，不直接污染情景记忆。
4. **外部记忆 Provider 契约**：把召回、写入、统计、能力描述和注销生命周期写成稳定接口，让未来的QQ桥、手机或其他记忆插件接入时不依赖内部表。
5. **记忆治理工作台**：把“为什么召回、为什么没召回、为什么被替代”做成用户可读的解释。

### 不应照搬

- “生活事件越多，记忆越强”没有自动成立；
- 把每日反思和互动纪念日直接写入长期记忆，可能制造大量低价值材料；
- 混合向量/关键词本身不是质量保证；必须继续保留Echo的时间纪律、相关性门控、降级提示和可回退路径。

## 三、情绪架构对比

### 对方项目的公开特点

它把角色生活、睡眠、疲倦、午休、日程、位置、天气、梦境、健康摘要和生活事件放进持续演进的状态系统，并让主动联系根据这些状态产生候选。情绪在其中更像“角色生活模拟”的一部分。

### Echo的不同强项

Echo当前更适合把情绪解释为两层：

- 整体状态：疲惫、valence、arousal等；
- 面向主人的关系状态：affection、playfulness、sadness、dependency等。

Echo还有：

- 同轮情绪读数；
- 情绪变化原因；
- 维度钳位；
- 时间衰减；
- 群聊时主人关系不转移给群友；
- 情绪只影响表达，不改变事实归属；
- 审计中的情绪变化和注入记录。

### 可借鉴的方向

1. **把情绪输入来源做成感知时间线**：对话、沉默、睡眠、主动行为、日记、群聊事件分别标明来源。
2. **增加状态解释而非更多维度**：用户能看到“这一轮为什么变累/变亲近”，但不能把内部数字直接当心理诊断。
3. **把情绪衰减与主动行为联动显示**：例如夜间压制、起床宽限期、主动关怀恢复。
4. **情绪状态版本化**：每轮保留上一轮、当前轮、变化和触发，不覆盖历史。

### 不应照搬

- 健康、饥饿、位置、天气等感知必须有真实授权和来源；
- 没有传感器或外部数据时不能虚构“生活”；
- 更多生活模拟不等于更准确的情绪理解；
- 不应为了宣传把状态字段变成模型必须复述的JSON。

## 四、主动行为和发送可靠性

这是对方项目最值得Echo吸收的部分。

README把主动消息描述成完整生命周期：

`角色生活/日程/睡眠/纪念日/未完话头 → 候选 → 时机/频率/权限 → 人格复核 → 发送前自检 → outbox/投递回执`

还公开描述了：

- 睡眠与起床宽限期；
- 浮动饭点；
- 48小时内未完话头语义复核；
- 纪念日派生；
- 表情/TTS意图在复核通过后再封装；
- 外部动作结果未知时不自动重放；
- 候选评估不阻塞普通聊天。

Echo已有主动关怀、想念、议程、提醒、发送审计和QQ发送边界，但仍可以补：

1. **统一主动候选状态机**：candidate、blocked、approved、queued、sent、unknown、expired；
2. **发送前复核记录**：为什么允许、为什么拦截、使用了哪些事实；
3. **outbox和结果未知语义统一**：尤其是QQ桥超时、部分发送、未知回执；
4. **主动行为和普通回复隔离预算**：候选规划不能拖慢正常对话；
5. **草稿中保留媒体意图**：TTS、表情、图片不在候选阶段直接发送，复核放行后再封装。

这些属于可靠性和可解释性升级，不需要引入对方的七项能力。

## 五、群聊与可见性

对方项目强调私聊和群聊严格隔离，群聊只读取公开档案和公开互动，不把成员私聊秘密、专属关系、健康/设备数据带入群聊。

Echo最近的多人群聊改动已经解决了人物归属、主人关系称谓、引用、补档重复和QQ尾号展示，但仍需在README中把边界写得像对方一样清楚：

- 主人关系只属于主人；
- 群友只能使用群公开事实；
- 补档不是当前发言，也不是发送证明；
- QQ尾号只用于区分参与者，不等于完整身份授权；
- 群聊上下文不等于私聊历史硬隔离；
- 共享会话/全局记忆的受众边界仍需谨慎。

## 六、工程和文档方面的借鉴

### 值得学习

- 版本升级交接与旧版回退材料；
- 独立SQLite运行库和覆盖升级隔离目录；
- 八步首次使用引导；
- 低配性能模式；
- Wiki、README、开发文档索引、扩展开发规范；
- 能力开关和局部降级；
- 运行统计、TTFT、工具、发送、Token、Prompt Cache和回执观测；
- 明确列出实际支持平台和兼容边界。

### Echo应该优先做的文档升级

1. README首页增加一张系统架构图；
2. 增加“第一次消息如何流过系统”的时序图；
3. 增加“记忆写入/读取/反思”三条独立链路；
4. 增加“情绪状态如何进入回复”的说明；
5. 增加“群聊可见性和QQ桥边界”章节；
6. 增加“普通回复、主动行为、反思任务”的调度边界；
7. 增加“已知限制和未解决问题”，避免把提示词边界写成隐私隔离；
8. 增加一个可复现的合成演示，不用真实账号和数据库。

## 七、建议的Echo升级优先级

### P0：文档和可解释性

- README重写架构章节；
- 记忆/情绪/群聊/审计时序图；
- 外部记忆Provider和窗口可见性契约草案；
- 主动候选生命周期和结果未知语义文档。

### P1：主动行为可靠性

- 统一候选状态机；
- 发送前复核快照；
- outbox和未知回执；
- 主动预算与普通回复隔离；
- TTS/图片/表情意图延迟封装。

### P2：记忆治理

- 记忆来源/可见性/替代链页面；
- 恢复队列和失败重试界面；
- 互动纪念日派生视图；
- Provider接口和能力握手。

### P3：有证据的生活感知

- 只接入用户明确授权且有来源的睡眠、天气、位置、屏幕或手机摘要；
- 每类感知都有来源、时间、权限和过期时间；
- 没有数据时显示未知，不让模型补造生活细节。

## 八、最终判断

这个仓库最强的不是“记忆算法比Echo先进”，而是它把陪伴产品做成了一个有生命周期、配置入口、后台候选、权限、发送回执和升级文档的完整系统。

Echo最应该借鉴的是它的**产品结构和可靠性契约**，而不是复制七项能力。Echo自己的记忆时间纪律、图谱证据、情绪关系维度、多人群聊身份修正和审计追踪仍然是核心特色；下一阶段应把这些能力讲清楚、连接起来、做成可观察的系统，而不是继续堆功能。
