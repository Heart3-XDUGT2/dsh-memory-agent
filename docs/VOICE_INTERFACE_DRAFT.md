# 语音通道 · 接口草案(给前端 TTS + Live2D)

> **状态:草案(P1 冻结形状、不实现)。** 2026-09-28 立。
> 2026-09-28 他给的实情:TTS 与 Live2D 由前端的人做,几天后对接,**能力是"边推理边输出、
> 一边出文本一边讲话"**(进度未知)。所以我们这边**先把稳定接口交出去**,别让他们等我们改协议。
> 实现排在 `docs/PLAN_CORTICO_ADOPTION.md` 的 P3/P4;本文只钉**形状与语义**。

## 0. 一句话定位

**唯一的"她"住在 DSH 与 `echo.db` 里。语音通道、QQ、以后任何面,都只是她的工具/通道** ——
不承载人格、不持有记忆、不是第二个主体。所以这份接口里没有"语音版的她",只有
「她在说话」这件事的**流式搬运**。

## 1. 三条不可谈判的边界(先说,因为它们决定接口形状)

1. **说过的话不能被抢回**(机械边界)。一个文本增量一旦**产生了外部输出**(TTS 已经出声 /
   Live2D 已经动嘴),此后**不再允许打断这一轮**。所以接口必须区分
   `externalized: false → true` 这一瞬;只有**尚未外化**的段可以被撤回。
2. **起草-确认门不上语音**。QQ 上那套"先草稿、再确认"靠多一轮推理换复核,**多一轮延迟** ——
   实时对话里是错的。语音要的是"边生成边外化 + 外化后不可撤"(上面第 1 条)。
3. **她不必每句都说完**。打断之后剩下的话**不重发**(否则会出现"她被打断后从头再讲一遍");
   未外化的部分直接丢弃,并**留一行痕**(她被打断过 —— 这是事实,要能查到)。

## 2. 我们提供给他们(主包 → 前端)

一个**增量文本流**,按"段"切,段内可增量:

```jsonc
// 每一条都是一个独立事件(名字待定,形状先钉)
{ "type": "seg.start",  "turnId": "t-20260928-1", "segId": "s1", "seq": 0 }
{ "type": "seg.delta",  "turnId": "t-20260928-1", "segId": "s1", "seq": 7,  "delta": "今天" }
{ "type": "seg.done",   "turnId": "t-20260928-1", "segId": "s1", "seq": 19, "text": "今天有点累," }
{ "type": "seg.external","turnId": "t-20260928-1", "segId": "s1", "at": 1759032000123 }
{ "type": "turn.end",   "turnId": "t-20260928-1", "reason": "done" }
```

字段语义(**这些是冻结的部分**):

| 字段 | 意思 | 谁需要它 |
| --- | --- | --- |
| `turnId` | 一整轮(她一次开口) | 打断只针对整轮 |
| `segId` | **一段 = 一个可独立播放、可独立撤回的单元** | TTS 拿它当播放队列的单元;与 QQ 的"气泡"**同一套 id 语义** |
| `seq` | 段内的序号(单调增,不保证连续) | 乱序/重发时对账 |
| `seg.done` | 这一段的文本**到此定稿**(之后不会再变) | TTS 可以放心把这一句播完 |
| `seg.external` | **她已经在外部出声了** ⇒ 从这一瞬起不可撤回 | 前端要在"开始播"那一刻回给我们 |
| `turn.end` | 整轮结束,`reason` 是**枚举**(`done` / `interrupted` / `error`) | 前端清状态 |

⚠️ **两种"结束"要分清**:`seg.done` = 这一句文本定稿(还没出声);
`seg.external` = 已经出声(不可撤)。**TTS 播完一句后应该回我们 `seg.external`**,
否则我们没法知道"哪些话已经泼出去了"。

## 3. 我们需要他们回给我们(前端 → 主包)

```jsonc
{ "type": "play.state", "segId": "s1", "state": "queued|speaking|done|aborted", "at": 1759032000456 }
{ "type": "asr.final",  "text": "你在干嘛呀", "ts": 1759031999000, "final": true }
{ "type": "asr.partial","text": "你在干",     "ts": 1759031995000, "final": false }
{ "type": "interrupt",  "turnId": "t-20260928-1", "reason": "user-barge-in" }
```

| 事件 | 为什么我们需要它 |
| --- | --- |
| `play.state` | ① 驱动"她正在说话"这个状态;② 与 QQ 的**送达回执同一形状**(QQ 那边 `ack` 才销账);③ 打断时我们靠它知道停在哪一句 |
| `asr.final` | 入站。**和 QQ 的私聊来信走同一条入站管道**(总闸/白名单/幂等/入队),只是 `channel: 'voice'` |
| `interrupt` | 他抢话。只对**尚未 external** 的段生效(第 1 条边界) |

## 4. 我们要问他们的四件事(**这几条我们不知道,得他们答**)

1. **能否中途停止播放**?能停到"字"一级,还是只能整句停?(决定打断的粒度)
2. **能否给逐字时间戳**(或逐字回调)?Live2D 口型对齐要用。(决定 `seg.delta` 要不要按字下发)
3. **"已播到哪"能不能回报**?(决定 `play.state` 是"句级"还是"字级")
4. **标点/语气标记**:他们希望我们**在文本里保留标点**(他们会自己断句),还是我们**按句切好再发**?

## 5. 还没定、要他拍的(不属于前端)

- **延迟预算**:ASR 结束 → 她开口,容忍多少毫秒?(这条决定后面能不能加任何"多一轮推理"的机制)
- **是否复用 `echo:relay`**:我倾向 **通道契约在脑侧、wire 复用 `echo:relay` 那一套**
  (推送只喊"有活儿"、正文留在账上、消费端 lease 取)—— 好处是一套 wire 两个通道;
  代价是要把"平台"这个维度真的用起来(今天只有 `qq`)。
- **分泡/保鲜期怎么映射**:语音没有"气泡",但有 TTS 分段。倾向**保留 `notBefore` 但改语义为"排队"**。

## 6. 现在的样子(别误会)

- **今天没有语音通道的实现**:仓库里既没有麦克风,也没有 TTS 播放 —— 他们做的那部分是**前端**。
- 今天有的是一条**传输**:`echo:relay`(主包 `ctx.provide`,QQ 插件消费),
  以及刚加的**契约自报** `hello() → {name, version, api:{min,max}, capabilities[]}` +
  **能力探测**(能力名对账,版本只做文案,单向宽容)。
- 所以对接的第一个动作是:**把本文第 2、3 节的形状冻住**,前端就能开始写;
  我们按 P3/P4 把语音通道按这份形状实现出来。
