## 零、三个漏洞是什么(以及为什么它们不用等评测集)

| # | 漏洞 | 为什么是**逻辑性**缺陷(与我的坏样本无关) |
|---|---|---|

## 一、全局分析

### 1.1 调用链(实测,不是推测)

```
活路径(Python,唯一真相)
  lib/engine.js:175   request('retrieve', {userId, query, topK})
    ↓
  python/worker.py:164  ftype == "retrieve"
    → retrieve.retrieve(conn, user_id, query, top_k, now)      [python/engine/retrieve.py:188]
        → rank_memories(rows, query, top_k, now)               [:130]  ← 漏洞①③ 在这里
        → 写回强化(forced 的跳过,见 F5)                        [:245-259]
    → render_episodic(items)                                   [:264]  ← 漏洞② 在这里
    → 帧回传 {items, text, reinforced}
  lib/engine.js:184   collectSeeds(frame.items, ...) → 图种子     ← 二阶影响见 1.2
  lib/engine.js:211   parts = 【关联知识路径】+【情景记忆】
  lib/engine.js:213   renderInjectedBlock({memoryText: parts})  ← JS 只做外壳排版
    ↓
  注入进系统提示

兜底路径(JS,仅 pythonDown 时)
  lib/engine.js:234   'python engine down — retrieve falls back to JS baseline'
  lib/store.js:511    rankMemories(rows.map(rowToMemory), ...)  [lib/retrieve.js:87]
  lib/context.js:324  renderMemoryList(memories)                ← 漏洞② 的 JS 侧

第二条检索入口(同一套打分,必须一起改或一起不改)
  python/worker.py:376  ftype == "memory_search"   ← 工具路径,复用 retrieve.retrieve()
```

**结论一:活路径只有一处打分器**(`rank_memories`),但同时被
**注入**与**工具**两条入口复用 ⇒ 改它等于两处都改(这正是我们要的)。
**结论二:注入文本由 Python 渲染**(`render_episodic` 是"渲染单一事实源"),
所以漏洞②的修点在 Python;JS 的 `renderMemoryList` 是兜底路径,为对齐也得同步。

### 1.2 三个漏洞各自的二阶影响(全局才知道的部分)

| 漏洞 | 直接影响 | **二阶影响(容易被漏)** |
|---|---|---|
| ① | 查不到该查到的记忆 | **(a) 图种子**:`collectSeeds` 拿记忆的 `keywords` 当图种子(F6)⇒ 关键词脏 = 种子脏(F6 现场那批 `'有什么想说的吗'`);**(b) 工具路径**同源 |
| ② | 她拿不相关的记忆答话(幻觉源) | **(c) 强化回写**:L0 虽被 F5 豁免,但"零命中轮次"的整体形态让**每一轮都长得一样**,审计与仪表盘上分不出"切题"与"只是常在场";**(d) 她的语气**:空转的 L0 挤占席位,可用的料变少(与"冷"同源) |
| ③ | top_k 被同义塞满 | **(e) 强化回写**:同一事实的 5 条**各自** `recall_count+1`、各自延长半衰期 ⇒ 冗余被反复喂大;**(f) 指标失真**:`recall_count` 作为"被想起次数"的语义被稀释 |

### 1.3 关键约束(不可回退)

1. **L0 常在场语义必须保住**:L0 零命中也进池、`core_cap = min(8, max(1, top_k-2))`、
   纯强制占位**不写回强化**(`forced` 标签,F5)。漏洞②要改的是**"她以为它与本轮有关"**,
   **不是**"L0 不许在场"。这两件事必须分开动手。
2. **双实现 + 差分锚点**:两侧有 NOW=1700000000 基准行逐点对表
   (`tests/retrieve.test.js` + `python/tests/test_retrieve.py`)。改打分 ⇒ 必须同步两侧并重对锚点。
3. **零第三方依赖**;不引 jieba、不引向量库。
4. **生产库只读**。打分是纯函数改造 ⇒ **不需要数据迁移**。
   ⚠️ 唯一例外:`retrieve.retrieve()` 会**写回强化**(`half_life`/`recall_count`/`last_recalled`)——
   所以**任何真实检索都会改库**。验证一律走测台(它只调 `rank_memories`,不写库)或副本。
5. **`memory_search` 的返回形状是协议**:`worker.py:397-407` 的字段被工具消费,改结构要谨慎。

## 二、施工项

### RT0 评测集重建(验收地基,查询先于答案)

- 改哪里:`scripts/retrieval-bench.py`
- 改法:
  * **取题来源(独立于答案)**:① 他真实说过的话(`conversation_log`,已取出 24 条,
    其中 12 条词面钩子 <20%);② 借 LongMemEval/LoCoCo 的题型配额(单会话事实 /
    多会话 / 时间推理 / 知识更新 / 矛盾消解 / 偏好);③ (可选)盲改写 ——
    **由不读库的独立 agent** 把 ① 改写成同义/口语/省略版
  * **硬规则:先取题,后标答案;标答案时不许改题面**
  * **覆盖率指标**(分母 = 全部记忆,不是我挑的题):**可达率** —— 每条记忆用"弱线索"
    (半段摘要 / 一个非关键词 / 指代)去查,能否在 top-K 找回自己
  * **硬塞率**:闲聊/负控档里 L0 被当相关记忆注入的比例(现状 3/3)
  * **偏差体检**(以后每份评测集都要报):`M1` 题面词元出自答案的比例(现状 69.8%)、
    `M2` 真实问法钩子率(现状 30.7%)
- 验收:分档报数;M1 显著低于 69.8%;可达率与硬塞率都出数。
- 风险:真实问法偏短 ⇒ 命中率天然低,**必须分档**,不能被它带偏。

### RT1 词元层(双实现)

- 改哪里:`python/engine/lexical.py`(新)、`lib/lexical.js`(新)
- 改法:`normalize`(NFKC + locale 无关小写)、`tokenize`(CJK 连续段切 **二字组合** +
  段内保留 2~16 字整串 + **丢弃单字** + Latin/数字/标识符)、`STOPWORDS`(自制最小表)
- 验收:两侧同输入同输出;停用词前后对照进提交信息(实测 85.2% → 88.9% 那次就是它的功劳)。
- 风险:停用词是双刃(切多了丢召回,「大一」被切掉就查不到 #121)⇒ 表由**测台量**,不靠感觉。

### RT2 索引正文 + BM25 打分(漏洞①,双实现)—— 核心

- 改哪里:`retrieve.py` 的 `hit_score`/`rank_memories`;`lib/retrieve.js` 同名函数
- 改法:
  * 打分改用 **BM25**:`idf = log(1+(N-df+0.5)/(df+0.5))`、
    `sat = tf(k1+1)/(tf + k1(1-b+b·dl/avgdl))`(k1=1.2, b=0.75),对查询词做
    **idf 加权覆盖率**并归一化到 [0,1]
  * **索引正文 = `summary` + `keywords`**(两样都要:keywords 里有 `derive_keywords`
    产的 CJK 二元滑窗,那是短查询的主力 —— 见 `episodic.py:derive_keywords` docstring)
  * 总分 = `w_rel·覆盖率 + w_rec·R + w_emo·情感`(配比见"待裁决①")
  * L0 豁免 / 强制占位 / `forced` 标签**原样保留**
- 验收:测台复跑(分档 + 覆盖率);`test_retrieve.py` / `retrieve.test.js` 全绿;
  耗时不得劣化(实测 BM25 比现状快约 8 倍)。
- 风险:keywords 字段是**异质**的(二元滑窗 / LLM 整句 / 反射层的逗号串)——
  `parse_keywords` 的逗号回落必须继续生效,否则反射层记忆的二元钩子全丢。

### RT3 零命中呈现(漏洞②,双实现渲染)

- 改哪里:`retrieve.py` 的 `rank_memories`(打标记)+ `render_episodic`(改渲染);
  `lib/retrieve.js` + `lib/context.js:renderMemoryList` 同步
- 改法:
  * 检索层**不变**(L0 照常在场);新增**"本轮是否有任何主题命中"**的标记
    (每条 item 标 `matched`,并在返回值里给一个整轮级的 `topicMatched`)
  * 渲染层:**当整轮零主题命中**时,给这块加一句标注,告诉她这批是**长期身份**、
    **不要拿它回答眼前的问题**;有命中时**照旧**(不加任何标注,避免噪声)
  * `memory_search`(工具路径)也拿到这个标记 —— 让工具能说"没找到"而不是报一堆 L0
- 验收:负控场景下(库里确实没有)注入块带标注;`量子纠缠` 类查询不再出现"拿 #125 答话";
  有命中的轮次渲染**逐字节不变**(回归)。
- 风险:措辞直接影响她的语气,改重了会变成"我没记住"的自我否定 ⇒ **措辞待裁决③**;
  另:`items` 增加字段会动差分锚点,RT6 要一起重对。

### RT4 去冗余(漏洞③,双实现)

- 改哪里:`rank_memories` / `rankMemories` 末尾
- 改法:近重复抑制(字符二字 Jaccard,阈值**由测台扫**后再定),在 L0 与常规结果
  **合并之后**做(否则同一事实会从两个通道各进一条)
- 验收:冗余率 ≤1% 且命中率不降;阈值曲线进提交信息。
- 风险:抑制过狠会让某些查询只剩 1~2 条(阈值 0.55 下「数据结构」只剩 1 条)
  ⇒ 需要**下限保底**。另:去冗余后强化回写条数会变少 —— **是修好,不是副作用**,写进提交信息。

### RT5 L0 / F5 语义回归钉死

- 改哪里:`python/tests/test_retrieve.py`、`tests/retrieve.test.js`
- 改法:把约束 1 的三条写成**显式回归**:L0 零命中在池 / `core_cap` 公式 /
  `forced` 不进强化回写。**先钉测试再改代码**(RT5 排在 RT2 之前)。
- 验收:三条各有独立断言;故意破坏一条能让测试红。
- 风险:这是最容易被"顺手优化"掉的地方(F5 之前踩过:`#125` `recall_count` 涨到 2463)。

### RT6 差分锚点对齐与注释同步

- 改哪里:`tests/retrieve.test.js`、`python/tests/test_retrieve.py` 基准行;
  两侧模块 docstring(`retrieve.py` 顶部那段公式注释现在会**说谎**,必须改写)
- 改法:两侧基准行逐点重对;把新公式、新字段(`matched`)、去冗余规则写进两边注释。
- 验收:两侧输出逐点一致;`npm run check` / `hygiene` 0。
- 风险:JS `rowToMemory` 与 Python 行字典字段名不同 ⇒ 要确认**喂进打分器的是同一份文本**
  (摘要与关键词的拼接方式必须逐字节一致)。

### RT7 测台纳入口径

改检索必须复跑 `scripts/retrieval-bench.py`,前后数字(分档 + M1/M2 + 覆盖率)进提交信息。
